# 03 · v1 已知不做的事

**2026-10-08** ｜ 契约 v1

这份文件记录 v1 **刻意不做**的东西，以及每一条会带来什么后果。
写下来是为了让后来的人不把「没做」误读成「忘了做」，也不把后果当成新 bug 去查。

---

## 一 ~~跨轮不带工具历史~~（2026-10-08 已补）

**已实现。** 工具调用落`toolCalls` 表，`buildModelMessages` 按 `seq` 重建
`assistant(tool-call part)` + `tool(tool-result part)`。

验证：`npm run verify:history`（13 条断言），其中最要紧的三条是
**并行顺序**、**call/result 一一对应**、**悬空调用不进上下文**。

**踩到的形状问题**：`ai@7` 用的是 content 数组（`{type:'tool-call'}` /
`{type:'tool-result', output:{type:'text',value}}`），
**不是 v5 那套 `{toolCalls, toolCallId}` 字段**。写错的症状是 provider 报 400
且不指出形状问题。改 SDK 大版本时这里第一个要验。

⚠️ **剩下的限制**：只取最近 6 轮的工具调用（`recentToolCalls` 的 `runLimit`），
超出的会被截断。长任务超过 6 轮之后模型会忘得更早 —— 
**截断策略是「按轮不按行」，按行截会把一轮切一半**（上下文里出现半个 tool-call，
那会让 provider 直接 400）。

## 一之二 审批结论只做成「下一条消息」，不做真正的挂起恢复

**没做**：跨进程恢复一个卡在审批上的 run。

**后果**：页面关掉再打开，那一轮要重新问一遍。

**为什么现在能接受**：审批只能由同一页面上的用户点击，而页面开着就不会忘。
真要恢复，HMAC 签名那条链路（契约 §五）还没在真实模型上验过 ——
现在做等于在一个没验证的机制上再叠一层状态机。

---

## 二、SOP Store 完全没实现

**没做**：没有 SOP、没有 Candidate / Approved 两态、没有从执行记录里提取经验。

**后果**：Agent 每次都从零开始。同一类任务重复问，重复摸索。

**为什么现在能接受**：契约 §七 把它列为不属于 Runtime 的数据 —— 它是**运行时经验**，
而 v1 连可靠的执行记录都还没攒够。没有 50 次真实运行，提取出来的「经验」只是噪声。

**注意**：**不要拿它当业务数据库用。** 想存业务数据，去 atlas / navi / raven。

---

## 三、不做多租户、不做长期记忆

**没做**：没有用户 ID、没有配额区分、没有向量记忆。

**理由**：一用户一实例（契约 §七）。隔离靠部署架构，不在业务模块里重复实现租户逻辑。
长期记忆在原讨论里已裁定暂缓。

---

## 四、不做流式工具执行

**没做**：工具内部的进度不流式。

**后果**：`tool.called` → 沉默 → `tool.completed`。跑一个 30 秒的脚本时，
UI 上那30 秒是空的。

**为什么现在能接受**：工具的输出当作一步的结果整体返回。
raven 的脚本运行台已经有自己的 SSE（`scripts-runner`），将来直接接那条流即可 ——
**工具的输出格式不是契约的一部分**。

---

## 五、进行中的 run 不跨重启恢复

**没做**：进程重启后，`running` 的 run 被标成 `interrupted`，不恢复执行。

**后果**：部署一次会打断一个会话的当前轮次。

**为什么这样**：半轮对话的工具结果已经丢了一半，硬接会产出比「明确中断」糟得多的东西。

**`interrupted` 不是 `run.failed`**：它没有 `code`，是一段历史，不是一个错误。
UI 应显示成「这一轮中断了，可以重新问一遍」。

---

## 六、单进程单run

**没做**：同一个会话同时只能跑一轮（契约 §三 的 409）。

**后果**：两个浏览器标签页发同一个会话，第二个拿到 409。

**为什么现在能接受**：这是单用户场景，而 UI 是单页的。
真要并发再说 —— 那是`runs` 表加个队列的事，但**现在加就是没有测试覆盖的代码**。

---

## 七、没有输入长度限制

**没做**：不截断过长的 `content`。

**后果**：极长的输入会直接进模型，可能触发模型的上下文上限 → `model_error`。

**为什么这样**：**截断是静默的数据损坏**（raven 的剪切板 `maxTextBytes` 就是同一个理由
选择拒绝而不是截断）。要加就加显式拒绝 + 明确的字节数。

---

## 八、审批没有超时

**没做**：`approval.requested` 之后，run 无限期挂着等人。

**后果**：一个忘记关掉的审批会永远占着那个会话的 409 锁。

**为什么现在能接受**：审批只能由同一页面上的用户点击，而页面开着就不会忘。
真要超时，得先想清楚超时后应该「拒绝」还是「自动批准」——**默认拒绝**是安全的一侧，
但那需要一个新的终止原因，而终止原因的集合是契约。

---

## 附二：镜像带着 devDependencies

**没做**：构建期没有把 TypeScript 编译成 .js，运行时用 `node --import tsx src/main.ts`。
所以镜像里必须保留 `tsx`（它在 devDependencies 里），连带 tsc 那一坨。

**后果**：镜像比 raven 大不少，且启动多一层 tsx 的编译开销。

**为什么这样**：编译成 .js 要改 `tsconfig` 的模块解析（`.ts` 扩展名 import 在
NodeNext 下必须写全，这是 tsx 在帮我兜），改完还要重新验一遍所有相对导入。
**先把服务跑起来，体积是下一步的事** —— 而这个体积问题是可测量的，
不像「跨轮工具历史」那种要攒够真实用例才知道对不对。

**什么时候做**：镜像超过 500MB 的时候。

---

## 附三：`raven.*` 工具只有只读

**没做**：raven gateway 的写操作（`files.write` / `files.remove` /
`clipboard.add` / `scripts.run`）全部返回 **501 + 说明为什么**。

**后果**：agent 只能看，不能动。

**为什么现在能接受**：契约 §五 的授权流程只在 `removeFile` 这个**必然失败**的
工具上验过（`npm run verify:approval` 9 条断言）。拿一个真能删文件的工具去验审批，
一旦审批链路有洞就是真的删掉了东西。**先让危险动作在一个无害的地方验证一遍。**

**什么时候做**：接通真key 的模型、跑通完整的「审批 → 执行」之后。
放开时的顺序：先 `clipboard.add`（可逆、影响小），再 `files.write`，
最后才是 `files.remove` 与 `scripts.run`。

---

## 附：接 raven 真实工具时要注意

1. **路径判定在 raven 那边，不在 agent。** agent 只调`/api/agent/gateway`，
   越界判定走 raven 的 `backstage/lib/sandbox.ts`。**不要在 agent 里复制一份路径检查** ——
   那会是两套会漂移的判定。
2. **新的工具声明 `risk: 'write'` 或 `'destructive'` 就自动触发审批**，不用在别处登记。
3. **工具名是契约。** 改 `name` 等于破坏契约；`inputSchema` 加必填字段也是（§八）。
4. 工具的 `description` **是给模型看的**，比 UI 文案重要得多 —— 它决定模型会不会用这个工具。
